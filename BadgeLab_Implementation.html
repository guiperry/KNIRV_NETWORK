1. Scope Overview

The current Badge Lab (badge-lab-panel.tsx) is an admin-only dashboard tab that generates a single badge SVG and mints it directly to chain. There is no "template" concept — each badge creation is a one-off mint. The DVE Workspace Policy panel (policy-editor.tsx) has no badge awareness. The WebGUI Vault (vault.js) has a tabbed interface for models/wallets/skills/capabilities/properties but no Badges tab. The goal is to bridge all three surfaces.

Three Integration Targets
  1. Badge Template System — The Badge Lab evolves from single-badge minting to a Template Registry. Admins define badge templates (named, typed, with preset parameters) that become reusable, referenceable blueprint objects.
  2. DVE Workspace → Policy Panel — When a user opens the Policy panel inside the DVE Workspace modal, they can browse available badge templates and attach them to the active DVE.
  3. WebGUI Explorer → Vault → Badges — The WebGUI Vault gets a new "My Badges" tab (modeled after the "My Properties" page pattern) and a "Badges" nav link in the Vault section of the SideNavigation. All users see the Vault.
Key Principle: Badge Templates are blueprints, not minted NFTs. Minting happens when a user/workspace attaches a template to a DVE. Templates live in a new backend registry (separate from the chain-based NFT registry) and are served to both the KNIRVSERVER dashboard and the WebGUI via a shared API.

3. Data Model: BadgeTemplate

A new Go struct lives in a new file backend/internal/services/badge/template.go (or a new backend/internal/services/badge_template/ package):

// BadgeTemplate is a reusable blueprint for minting badges. type BadgeTemplate struct { ID string `json:"id"` // UUID Name string `json:"name"` // e.g. "Certified Validator" BadgeType string `json:"badge_type"` // "skill", "capability", "property" Description string `json:"description"` // Human-readable ValueSignals []string `json:"value_signals"` // Selected Values OntologySignals []string `json:"ontology_signals"` // Selected Ontology AITextTag string `json:"ai_text_tag"` // e.g. "Confidential • v2.1" PrimaryColor string `json:"primary_color"` // hex SecondaryColor string `json:"secondary_color"` // hex BackgroundColor string `json:"background_color"` // hex AlignmentThreshold float64 `json:"alignment_threshold"` AuthCredentials AuthCredentialSet `json:"auth_credentials"` // API keys, JWT, roles SVGDesign string `json:"svg_design"` // pre-rendered SVG (optional cache) CreatedAt time.Time `json:"created_at"` UpdatedAt time.Time `json:"updated_at"` IsActive bool `json:"is_active"` // soft delete / archive } type AuthCredentialSet struct { APIKeyProvider string `json:"api_key_provider,omitempty"` APIKeyScope string `json:"api_key_scope,omitempty"` JWTClaim string `json:"jwt_claim,omitempty"` JWTValue string `json:"jwt_value,omitempty"` SelectedRole string `json:"selected_role,omitempty"` }
Storage: For Phase I, use an in-memory registry with JSON file persistence at /var/lib/knirvserver/badge-templates.json. This reuses the existing application data directory already allocated for KNIRVSERVER. The registry auto-detects the directory (checks for /var/lib/knirvserver/ existence, or uses KNIRV_DATA_DIR env var as override). Thread-safe (sync.RWMutex), loads on startup, saves on mutation.

8. Pitfalls & Risks

⚠️ Watch Out For
  1. CORS/Same-Origin on WebGUI API calls. The WebGUI lives in KNIRVGATEWAY (port 8888), but badge template data lives in KNIRVSERVER (port 8084 via KNIRVROUTER). The WebGUI's api.js utility must be configured to proxy or reach the KNIRVSERVER API. Check if there's already a gateway proxy route; if not, add one in KNIRVGATEWAY/internal/server/server.go.
  2. Auth propagation. The my-badges.js WebGUI page needs the same JWT/auth headers that the vault page uses. Verify the api.js utility includes auth tokens for cross-service calls.
  3. Template SVG regeneration. When a user edits a template (e.g., changes values or colors), the SVG must be regenerated. Do this server-side in the UpdateTemplate handler by calling badge.GenerateBadgeSVG() again.
  4. JSON file persistence race. If the server crashes between Save() calls, the last N templates could be lost. For Phase I this is acceptable; for production, add write-ahead logging or move to SQLite.
  5. Existing mint flow coupling. The /mint endpoint currently goes through knirvshell.Service.CreateBadge() which mints to KNIRVCHAIN. The template mint endpoint should reuse this path so that badges minted from templates are real on-chain tokens with all the ICME/guardrail/WASM enforcement.
  6. Admin-only vs all-user. The Badge Lab (create/edit templates) is admin-only. The WebGUI Badges page (view + mint from templates) is all-users. The DVE Workspace Policy panel (attach templates to a DVE) is DVE-owner role. Ensure route-level authorization is correct.
  7. Vault.js controller gate removal. The current vault page hides all content behind knirvControllerConnected. Changing this to show badges by default requires careful testing to ensure existing functionality (models, wallets, etc.) still gates on controller connection where needed.
