KNIRVROOT Database Definition Protocol
Version: 1.0 Date: October 26, 2023

1. Overview

This document defines the database architecture for the KNIRVROOT platform. The system utilizes a dual-database strategy to ensure data integrity, transactional consistency, and advanced search capabilities:

LevelDB: Serves as the primary, persistent datastore for all canonical blockchain data, including blocks, transactions, and account states. It is the source of truth.
Chromem-go: Functions as a secondary, in-memory (with on-disk persistence) vector database. It provides a searchable cache, enabling semantic search and efficient querying of data derived from the LevelDB blockchain. It uses a custom Cerebras embedding function for generating vector representations of textual data.
2. LevelDB: Primary Blockchain Datastore

2.1. Purpose:

To provide an immutable, append-only ledger of all confirmed blocks and transactions.
To store the current state of the blockchain, including account balances and registered capabilities.
To act as the definitive source of truth for all blockchain-related information.
2.2. Data Stored:

Blocks: Full block data, including headers, transaction lists, proposer addresses, and hashes (as defined in block.go).
Transactions: Individual transaction details (as defined in transaction.go).
Account Balances: NRN token balances for user addresses (managed via LevelDB.SaveAccountBalance, LevelDB.GetAccountBalance in leveldb.go).
Capability Descriptors: Persisted state of registered MCP capabilities (e.g., types.ResourceDescriptor, types.ToolDescriptor stored as protobuf messages via LevelDB.SaveCapability, LevelDB.GetCapabilityByID in leveldb.go).
Context Records: Records of capability invocations and interactions (e.g., types.ContextRecord stored as protobuf messages via LevelDB.SaveContextRecord, LevelDB.GetContextRecord in leveldb.go).
Blockchain Metadata: The serialized BlockchainStruct itself, containing the current chain, transaction pool, and other metadata, keyed by ChainID (managed via LevelDB.PutIntoDb, LevelDB.GetBlockchain in leveldb.go).
2.3. Key Characteristics:

Persistence: Data is durably stored on disk.
Atomicity: Operations are designed to be atomic where necessary (e.g., balance updates during transaction processing).
Source of Truth: All data indexed in Chromem-go is derived from and can be rebuilt from LevelDB.
2.4. Interaction & Initialization:

The LevelDB struct in leveldb.go wraps the github.com/syndtr/goleveldb/leveldb client.
Initialized via NewLevelDB(dbPath) (e.g., in main.go during startNode or GUI pre-initialization).
The path is determined by cfg.BlockchainDatabasePath (from config/config.go), which is resolved by config.GetBlockchainDatabasePath or config.GetReflectionDatabasePath based on the node's role and configuration.
Core blockchain operations (adding blocks, processing transactions) within BlockchainStruct (in blockchain_struct.go) interact with LevelDB to read and write state.
3. Chromem-go: Searchable Data Cache and Semantic Index

3.1. Purpose:

To enable fast, semantic search across blockchain data (transactions, capabilities, context records).
To provide a readily queryable local cache of this data, reducing load on LevelDB for search operations.
To support complex filtering based on metadata alongside vector similarity searches.
3.2. Data Stored (Collections): Chromem-go stores data in collections. Each collection typically contains documents, their vector embeddings, and associated metadata.

transactions Collection:

Documents: Natural language representation of transaction details, suitable for embedding. Generated by PrepareTransactionForChromem (in chromemDB_conversion.go and used by ChromemSyncManager.OnNewBlockConfirmed in sync_manager.go, and ChromemManager.AddTransaction in chromemDB_manager.go).
Metadata: Key-value pairs including TransactionHash, BlockHash, BlockNumber, From, To, Value, Type, Timestamp, Fee, Status, DataType, BlockHeight, BlockTimestamp.
IDs: Transaction hashes.
context_records Collection:

Documents: Natural language summary of the context record. Generated by PrepareContextRecordForChromem (in chromemDB_conversion.go and used by ChromemSyncManager.OnNewBlockConfirmed, and ChromemManager.AddContextRecord).
Metadata: Key-value pairs including ID, CapabilityID, InvokerNRN, ProviderNRN, Status, InputDataHash, OutputDataHash, Error, TimestampInitiated, TimestampCompleted, GasFeeNRN, TransactionHash, BlockHeight, BlockTimestamp.
IDs: Context record IDs.
capability_descriptors Collection:

Documents: Natural language description of the capability. Generated by PrepareCapabilityDescriptorForChromemFromRegister, PrepareCapabilityDescriptorForChromemFromUpdate (in chromemDB_conversion.go and used by ChromemSyncManager.OnNewBlockConfirmed, and ChromemManager.AddCapabilityDescriptor).
Metadata: Key-value pairs including ID, Name, Owner, Version, Description, CapabilityType, GasFeeNRN, RegisteredAt, TransactionHash, BlockHeight, BlockTimestamp, IsLatest (boolean flag).
IDs: Capability IDs.
3.3. Key Characteristics:

Vector Database: Stores and indexes dense vector embeddings of documents.
Semantic Search: Allows querying based on the meaning/similarity of text.
Metadata Filtering: Supports filtering results based on metadata fields.
3.4. Persistence:

Utilizes chromem.NewPersistentDB(path, compress) as seen in NewChromemManager (chromemDB_manager.go) and NewChromemSyncManager (sync_manager.go).
The path parameter is derived from cfg.SearchableDatabasePath (from config/config.go), which is typically resolved by config.GetSearchableDatabasePath during node installation or startup. The expected path format is app_data/role_data/role_data.db (conceptually, the actual path is generated).
chromem-go documentation indicates that persistence is done synchronously on each write operation, with each document addition potentially leading to a new file (gob encoded).
3.5. Embedding Function:

A custom embedding function is used, leveraging the Cerebras inference platform.
The github.com/guiperry/chroma-go_cerebras/pkg/embeddings/cerebras.NewEmbeddingFunction is initialized (e.g., in NewChromemSyncManager and NewChromemManager).
Configuration for Cerebras (API key, base URL) is provided via ChromemConfig.CerebrasConfig (defined in sync_manager.go and populated from the main application config, e.g., cfg.Chromem.CerebrasConfig in main.go).
An adapter function is used to match the chromem.EmbeddingFunc interface:
go
// In NewChromemSyncManager (sync_manager.go)
adapter := func(texts []string) ([][]float32, error) {
    vectors, err := ef.Embed(texts) // ef is the cerebras.EmbeddingFunction
    if err != nil { return nil, err }
    return vectors, nil
}
csm.ef = adapter
This csm.ef (or an equivalent in ChromemManager) is then passed to client.GetOrCreateCollection for each collection.
3.6. Synchronization (ChromemSyncManager - sync_manager.go): The ChromemSyncManager is responsible for keeping Chromem-go in sync with the LevelDB blockchain.

Initialization: An instance of ChromemSyncManager is created within NewBlockchain (blockchain_struct.go) and associated with the BlockchainStruct.
OnNewBlockConfirmed(block *Block):
Iterates through transactions in the newly confirmed block.
Uses helper functions (e.g., PrepareTransactionForChromem, PrepareContextRecordForChromem, PrepareCapabilityDescriptorForChromemFromRegister, PrepareCapabilityDescriptorForChromemFromUpdate from chromemDB_conversion.go) to transform blockchain data into documents and metadata suitable for Chromem-go.
Adds these prepared items to the respective Chromem-go collections using collection.Add().
For capability updates, it queries the capability_descriptors collection to find the previously "latest" version and updates its IsLatest metadata to false before adding the new version as IsLatest: true.
OnBlockOrphaned(block *Block):
Identifies data in Chromem-go collections associated with the orphaned block (typically by filtering on BlockHeight metadata).
Uses collection.Delete() to remove these orphaned entries.
For capability descriptors, if an orphaned descriptor was IsLatest: true, this method queries for the version that was latest before the orphaned block and updates its metadata to IsLatest: true.
3.7. Querying (ChromemManager - chromemDB_manager.go & transaction_search.go): The ChromemManager provides an interface for querying Chromem-go, primarily for API endpoints.

Initialization: An instance of ChromemManager is created (e.g., in main.go if the GUI or API server is active), configured with the SearchableDatabasePath and CerebrasConfig.
Search Endpoint: The /api/transactions/search endpoint (handler in transaction_search.go) uses ChromemManager.SearchTransactionsChromem.
SearchTransactionsChromem:
Constructs a query based on SearchTransactionsRequest (semantic query text and metadata filters like Type, From, To, Timestamp, Value).
Calls m.transactionCollection.Query(ctx, semanticQuery, nResults, whereFilter, nil) to execute the search against Chromem-go.
Processes and returns the results.
Direct Additions: ChromemManager also contains methods like AddTransaction, AddContextRecord, AddCapabilityDescriptor. These seem intended for adding individual items to Chromem-go outside the main blockchain sync loop, potentially triggered by direct API calls or other application events.
4. Data Flow Summary

Block Confirmation: A new block is validated and added to the BlockchainStruct.Blocks list and persisted to LevelDB.
ChromemDB Sync: ChromemSyncManager.OnNewBlockConfirmed is triggered. It processes the new block, prepares relevant data (transactions, context records, capabilities), and upserts/adds them into the corresponding Chromem-go collections. Embeddings are generated by the Cerebras embedding function.
Search Query: A client sends a search request to an API endpoint (e.g., /api/transactions/search).
Query Execution: The API handler calls ChromemManager, which constructs a query (semantic and/or metadata-based) and executes it against the appropriate Chromem-go collection.
Results: Chromem-go returns matching documents, which are then formatted and sent back to the client.
5. Configuration

LevelDB Path: Defined by cfg.BlockchainDatabasePath in config.Config. Resolved based on node role and environment.
Chromem-go Path: Defined by cfg.SearchableDatabasePath in config.Config. This path is passed to chromem.NewPersistentDB.
Cerebras Embedding Function: Configured via cfg.Chromem.CerebrasConfig (containing APIKey and BaseURL), typically loaded from environment variables or a configuration file.
This protocol should provide a clear understanding of how LevelDB and Chromem-go are utilized within your KNIRVROOT application.
