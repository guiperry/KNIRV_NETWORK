      #1489           🔵  Container Deployer Artifact Management Architecture
        The container deployer's artifact management system uses a hierarchical 
    directory structure to organize different types of deployment assets. The 
    os_builder artifacts (Kata container components) are stored separately in 
    the user's local share directory following XDG conventions, while general 
    application artifacts and embedded resources are stored within the 
    application data directory. This separation allows for clean organization 
    between build-time artifacts from os_builder and runtime deployment 
    resources. The main function initializes deployment logging with graceful 
    degradation—if logging setup fails, it prints a warning to stderr but 
    continues execution rather than failing completely. This design choice 
    ensures that deployment operations can proceed even if logging 
    infrastructure has issues, prioritizing operational availability over 
    perfect observability.

      #1490           🔵  Deployment Type Selection and Orchestration Logic
        The container deployer implements a two-path deployment strategy that 
    diverges based on deployment target. Users select between local and cloud 
    deployment either through a --deployType flag or an interactive menu prompt.
     The system validates this choice strictly, accepting only "local" or 
    "cloud" values. Local deployments target Docker containers and invoke the 
    deploy-docker-app.yml Ansible playbook, passing the Go application source 
    path and desired container image name. Cloud deployments instead use Kata 
    containers (lightweight VMs) and invoke deploy-kata-app.yml, which requires 
    additional Kata-specific artifacts from the os_builder's artifact directory.
     This architectural split allows the same deployment orchestrator to handle 
    both development/testing scenarios (Docker) and 
    production/security-sensitive scenarios (Kata) while maintaining consistency
     in the deployment workflow. The use of Ansible playbooks provides 
    declarative infrastructure-as-code configuration for both paths.

    building Docker image with Kali tools. The build process was examined 
    through error logs showing DNS resolution failure at kali.download 
    repository. The containerfile-kali.j2 template was identified as the 
    Dockerfile being used, which installs ca-certificates, strace, gdb, tcpdump,
     iptables, apparmor, and apparmor-utils from Kali repositories.

    Learned: The Kali Linux base image (kalilinux/kali-rolling:latest) downloads
     successfully from Docker Hub. DNS resolution failures occur during apt-get 
    update when the container tries to contact kali.download mirror for package 
    lists. The error manifests as "Temporary failure resolving 'kali.download'" 
    after multiple retry attempts over 98 seconds. This is a network-level 
    issue, not a Dockerfile configuration problem. The build fails at step 2/5 
    before any packages can be installed, preventing all subsequent tool 
    installations from completing.

    Completed: Diagnosis of the Docker build failure completed. Root cause
    identified as DNS resolution failure when accessing Kali package 
    repositories from within the Docker build context. The build infrastructure 
    appears properly configured with correct Dockerfile syntax and package 
    names.

    Next Steps: Need to resolve the DNS connectivity issue for Docker builds.
    Potential solutions include: configuring Docker daemon DNS settings, using 
    alternative Kali mirror repositories in the Dockerfile, adding DNS 
    nameservers to the build process, or investigating network/firewall issues 
    blocking access to kali.download from the build environment.

● Perfect! I can see docker0 exists now. The logs reveal the root cause: NetworkManager is trying to manage Docker bridge interfaces, which causes instability.

  Here's the permanent fix to prevent NetworkManager from interfering with Docker bridges:

  Permanent Solution:

  Create a NetworkManager configuration file to ignore Docker interfaces:

  # Create a configuration file to tell NetworkManager to ignore Docker bridges
  sudo bash -c 'cat > /etc/NetworkManager/conf.d/docker-bridge-unmanaged.conf << EOF
  [keyfile]
  unmanaged-devices=interface-name:docker*,interface-name:veth*,interface-name:br-*
  EOF'

  # Reload NetworkManager to apply the configuration
  sudo systemctl reload NetworkManager

  # Verify docker0 is now unmanaged
  nmcli device status | grep docker

  This configuration tells NetworkManager to NOT manage:
  - docker* - The docker0 bridge and any docker-created interfaces
  - veth* - Virtual ethernet pairs used by containers
  - br-* - Docker custom bridge networks

  Why This Fixes the Issue:

  Looking at your logs, NetworkManager was actively managing docker0:
  device (docker0): state change: unmanaged -> unavailable -> disconnected -> prepare -> config -> ip-config -> ip-check -> secondaries -> activated

  This management causes conflicts with Docker's own network management, leading to the bridge disappearing during operations.

  Issue 2: DNS Resolution Failure

  Containers can't resolve DNS names (deb.debian.org). This is because:
  1. Docker daemon doesn't have explicit DNS servers configured
  2. Containers may not inherit DNS from the host when docker0 is unstable
