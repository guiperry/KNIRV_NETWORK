# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[gotcha]** `dve-verification-iframe.tsx` port-scans `['8081', '8080', '8090']` to discover the gateway. In testnet/production the gateway runs on `:8888`. Set env var `NEXT_PUBLIC_GATEWAY_PORT=8888` (matching the configured gateway port) so the iframe finds the gateway without scanning the wrong ports.
- **[gotcha]** KNIRVHASHER uses TWO distinct Unix sockets: `hasher.sock` (HTTP, headless pipeline run/stop/status) and `hasher-grpc.sock` (gRPC, for data-connector `ExportSecurityData`/`TriggerTraining` calls). Connecting a gRPC client to `hasher.sock` produces the misleading error `http2: failed reading server preface` — it looks like a server crash but is a protocol mismatch. The gRPC socket path is derived as `<hasher_socket_path_without_.sock>-grpc.sock` when `HASHER_GRPC_SOCKET_PATH` is unset.
- **[env]** KNIRVHASHER socket env vars: `HASHER_SOCKET_PATH` → HTTP headless socket; `HASHER_GRPC_SOCKET_PATH` → gRPC socket. The data-connector subprocess only receives `HASHER_GRPC_SOCKET_PATH` if `knirvhasher.ManagerConfig.GRPCSocketPath` is set — it is not passed automatically. Always wire `hasherGRPCSocketPath` into `ManagerConfig.GRPCSocketPath` when constructing the hasher manager in `main.go`. Also: `data-connector`'s `LoadConfig` reads `HASHER_GRPC_SOCKET_PATH` (not `HASHER_SOCKET_PATH`) to dial the server — using the HTTP socket env var here triggers a silent protocol failure.
- **[gotcha]** `HasherExporter` in `internal/services/dve/hasher_export.go` (backend_server source, in the separate sibling `KNIRV_CORP` repo at `KNIRV_CORP/packages/server/backend_server/`, not under `packages/KNIRVSERVER/` in this repo) defaults to `localhost:50051` when no address is passed — this TCP address is wrong; the backend's gRPC server is on a Unix socket. Any caller must pass `"unix:<hasher-grpc.sock>"` explicitly or the export stream will immediately fail with a connection error.
- **[gotcha]** KNIRVHASHER pipeline stages in `packages/KNIRVHASHER/pipeline/` each have their own `go.mod` with shorthand local module names (`data-connector`, `data-mapper`, `data-encoder`, `data-trainer`; directories are `0_DATA_CONNECTOR`/`1_DATA_MAPPER`/`2_DATA_ENCODER`/`3_DATA_TRAINER`). Each stage must be built and tested from within its own subdirectory — they cannot be imported from or built via the root `packages/KNIRVHASHER/` module.
- **[gotcha]** `packages/KNIRVHASHER/pipeline/2_DATA_ENCODER`'s `AutoDetectInputFile()` searches for its input in `$KNIRV_APP_DATA_DIR/json/` and `~/.local/share/hasher/`, in priority order: `ai_knowledge_base_goat_alpaca.json` → `ai_knowledge_base_alpaca.json` → `ai_knowledge_base.json` → `.arrow` variants. If data-mapper (`1_DATA_MAPPER`) writes output to a different path than expected, the encoder silently falls back to a placeholder that doesn't exist and fails immediately with "input file does not exist".
- **[gotcha]** `packages/KNIRVHASHER/pipeline/0_DATA_CONNECTOR` connects to KNIRVSERVER via TCP gRPC (`grpc.NewClient(config.KNIRVSERVERAddr, grpc.WithTransportCredentials(insecure.NewCredentials()))`). To route through the Unix socket instead, the YAML config `knirvserver_addr` must use the `unix:` scheme (e.g. `unix:/path/to/hasher-grpc.sock`) — the address is passed verbatim to `grpc.NewClient`.
- **[gotcha]** Passing `--goat` to the knirvhasher CLI skips `0_DATA_CONNECTOR` entirely and fetches from HuggingFace (`stallone/goat` dataset) directly. Output filenames change from `ai_knowledge_base.json` to `ai_knowledge_base_goat_alpaca.json` — the encoder's `AutoDetectInputFile()` prefers the goat variant, so the pipeline still flows correctly. Remove `--goat` when you want the data-connector security export path instead.
- **[env]** `KNIRV_APP_DATA_DIR` must be set consistently for all KNIRVHASHER pipeline stages. `data-mapper` writes to `$KNIRV_APP_DATA_DIR/hasher/data/json/`; `data-encoder` reads from `$KNIRV_APP_DATA_DIR/json/`. If the env var differs between stage invocations or is absent in any stage, each falls back to its own directory resolution logic and the stages write/read from different paths, silently breaking the pipeline.
- **[gotcha]** `data-trainer` (CGo binary) links against `libcuda_hash.so` at build time, but the `.so` is NOT automatically included in `internal/cli/embedded/bin/`. At runtime the binary fails immediately with `exit status 127` ("cannot open shared object file"). After `make build-data-trainer`, also ensure `libcuda_hash.so` is present in the embed dir. The updated Makefile `build-data-trainer` target copies it automatically — older installs or manual builds require: `cp pkg/hashing/methods/cuda/libcuda_hash.so internal/cli/embedded/bin/`.
- **[gotcha]** The `data-trainer` pipeline stage in `controller.go` (`PipelineStage.Args`) previously had `-hash-method cuda` hardcoded, causing `exit status 127` on any machine without a GPU even when `libcuda_hash.so` is present. Always use `-hash-method auto` — it falls back gracefully to the software implementation when CUDA is unavailable.
- **[gotcha]** When KNIRVSERVER runs as root (e.g., `sudo ./backend_server`), the `data-mapper`'s embedded C++ Python bridge calls `site.getusersitepackages()` which resolves to `/root/.local/...`, not the invoking user's `~/.local/...`. spaCy models installed for the real user (like `en_core_web_sm`) become invisible and the pipeline fails with `OSError: Can't find model 'en_core_web_sm'`. Fix: `manager.go` now reads `SUDO_USER` and injects the correct `PYTHONPATH`; always start KNIRVSERVER via `sudo -E` or ensure `SUDO_USER` is preserved in the environment.
- **[gotcha]** `data-mapper` has `RUNPATH` baked in at build time pointing to the absolute source-tree path (`packages/KNIRVHASHER/pipeline/1_DATA_MAPPER/spacy/lib`) for `libspacy_wrapper.so`. On deployed machines where the source tree doesn't exist (e.g., `/var/lib/knirvserver/bin/data-mapper`), `ldd` will show `libspacy_wrapper.so => not found` and the NLP bridge silently fails to initialize. Either co-locate `libspacy_wrapper.so` with the binary or set `LD_LIBRARY_PATH` to include the source-tree lib path when running the deployed binary.
- **[gotcha]** `packages/KNIRVSERVER/config/production.yaml` currently ships with `feature_flags: ebpf: true`, `cognitive_engine: true`, `blockchain_integration: true` — all three are enabled by default (this was flipped from disabled at some point; if a stale doc or memory says otherwise, trust the YAML). If one of these still appears inert in a running deployment, check for a stale build rather than assuming the flag is off.
- **[gotcha]** When creating or updating `.socraticodecontextartifacts.json`, verify each artifact path actually exists before adding it. `Write` succeeds even with non-existent paths, and SocratiCode silently skips artifacts that don't resolve — making omissions impossible to diagnose without re-running `codebase_status`. Use `find <path> -maxdepth 1` to confirm paths before inclusion.
- **[gotcha]** The `knirvarena.tar.gz` bundle (created via `tar -czf ... -C dist .`) includes a root `./` entry that resolves to `destDir` itself during extraction. The path-traversal guard in `packages/KNIRVSERVER/pkg/knirvarena/embedded.go` (`!strings.HasPrefix(cleanTarget, cleanDest+sep)`) always rejects this entry — returning "illegal tar path" — because `cleanTarget == cleanDest` without the separator. The fix is to add `if cleanTarget == cleanDest { continue }` before the HasPrefix check. Without this, KNIRVARENA fails to extract on first launch and the arena directory remains empty.
- **[gotcha]** KNIRVARENA is served at the `/arena/` sub-path, so hardcoded root-relative public asset paths (e.g. `/assets/avatar/Green_Bot_Explorer.glb`, `/sounds/background.mp3`) resolve to the server root rather than under `/arena/`. The browser receives an HTML 404 page in place of the binary file, which Three.js/GLTF reports as `"Unexpected token '<', '<!DOCTYPE'...is not valid JSON"` — with no obvious connection to a path prefix issue. Always use `` `${import.meta.env.BASE_URL}assets/...` `` for all public asset references in KNIRVARENA source (`AIAgent.tsx`, `AnchorStraighteningSequence.tsx`, `GameArena.tsx`, `AgentManager.tsx`, etc.).
- **[pattern]** KNIRVARENA rebuild-and-embed workflow after source changes: (1) `cd packages/KNIRVARENA && npm run build` (~90s), (2) `tar -czf /tmp/knirvarena_new.tar.gz -C dist .`, (3) `mv /tmp/knirvarena_new.tar.gz packages/KNIRVSERVER/pkg/knirvarena/bin/knirvarena.tar.gz`, (4) rebuild KNIRVSERVER: `cd packages/KNIRVSERVER && go build -o dist/knirv-server .`. Note: this only relinks the already-vendored `backend_server` binary — rebuilding `backend_server` itself from source requires a checkout of the separate sibling `KNIRV_CORP` repo (`packages/server/backend_server`); it is not buildable from within this repo. Use absolute paths in `go build` invocations — the shell CWD resets between Bash calls and a wrong CWD produces silent failure (empty output, no error) rather than a clear build error.
- **[gotcha]** WebSocket `dve-node-discovered` payloads pushed from the backend into the frontend `use-dve-nodes` React Query cache must include ALL fields the `DVENode` renderer expects — especially `tee_type`, `location`, `capabilities`, `reputation_score`, `cpu_usage`, `memory_usage`, and all ISO 8601 timestamp fields (`last_heartbeat`, `created_at`, `updated_at`). When a node arrives via WS that is NOT already in the cache, `use-dve-nodes` appends the raw payload object directly without applying defaults. Any missing string field that a component calls `.toUpperCase()` on crashes the renderer with `TypeError: Cannot read properties of undefined`. Always send a fully-populated payload matching the `DVENode` interface, not a minimal summary.
- **[pattern]** KNIRVSERVER frontend rebuild-and-embed workflow: (1) `cd packages/KNIRVSERVER/frontend && npm run build`, (2) `cd packages/KNIRVSERVER && go build ./...`. The Next.js `out/` directory is embedded into the Go binary at build time — frontend changes are invisible in a running server until BOTH steps complete.
- **[gotcha]** `checkNodeHealth()` in `dvemanager/dve_manager.go` marks any DVE node offline if `LastHeartbeat` is older than 2 minutes. Container-based DVEs do NOT auto-send heartbeats — heartbeats only arrive via the P2P message path (`handleNodeHeartbeat`). A newly-created container DVE that is never reached by P2P will go offline within 2 minutes and vanish from the KNIRVGATEWAY WebGUI "My DVEs" list. When debugging DVE disappearance, check `LastHeartbeat` on the node record; the `Heartbeat` method in `node_lifecycle.go` can be called directly to keep a node alive.
- **[gotcha]** `dve-list.js` in the KNIRVGATEWAY WebGUI fetches `/api/dve-nodes` and client-side filters for `status === 'online'` only. A node stored in BuntDB under any other status (`pending`, `offline`) will not appear in the list regardless of what the backend returns. KNIRVGATEWAY proxies `/api/dve-nodes` directly to the backend socket (not via `/api/v1/`); the canonical new path is `/api/v1/dve/nodes` but the WebGUI still uses the legacy path.
- **[gotcha]** `CreateDVENode` in `dve_creation_service.go` creates the DVE record with `status: "pending"` and only transitions it to `"online"` after `ContainerOrchestrator.ProvisionContainer()` succeeds and calls `UpdateNode`. If container provisioning is slow, fails silently, or `dveManager` is nil at creation time, the node stays `"pending"` forever and never appears in the WebGUI DVE list. Separately, DVE creations are stored under `dve_creation:` keys; DVE nodes (what the list queries) are stored under `dve:nodes:` keys — these are two independent records that must both exist.
- **[gotcha]** `packages/KNIRVSERVER/pkg/knirvagent` has its own `go.mod`, separate from `packages/KNIRVSERVER` (wrapper) — and from `backend_server`, whose source is in the separate sibling `KNIRV_CORP` repo, not under `packages/KNIRVSERVER/` here. Build and test it by running `cd packages/KNIRVSERVER/pkg/knirvagent && go build ./...` — running `go build ./pkg/knirvagent/...` from any parent directory fails silently or with a module error.
- **[gotcha]** `AgentManager.StartAgent` in `pkg/knirvagent/manager.go` holds a write lock (`am.mu.Lock()`) while building the subprocess command; calling any helper that tries to acquire an RLock on the same mutex (e.g., `applyWorkspaceResolver`) produces a deadlock. Symptom: `go test` hangs for 600s then fails with `sync.RWMutex.RLock` in the goroutine dump. Fix: snapshot all mutex-protected fields into local variables before releasing the write lock, then call helpers after the unlock.
- **[gotcha]** `GetSupervisorAgentStatus` must NOT call `HealthCheck` (which dials the agent socket over HTTP with a 3s timeout) — the endpoint runs behind a 1-minute proxy timeout and a blocked health check causes a 503 after the full 60s. Use only `GetSocketPathForDVE` (socket file stat + 250ms dial probe) to determine agent liveness.
