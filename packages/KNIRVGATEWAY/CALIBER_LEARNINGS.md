# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[correction]** `Bracket.Memory` is 18 bytes (wire bytes 43–60, slots 6–8), not 14. Using `[14]byte` for Memory misaligns GoldenSeed out of its canonical slot at 61–64 and breaks the wire layout.
- **[correction]** Wire byte 36 (slot 4) is a single packed byte encoding POS (low nibble), tense, and plurality via `PackSyntacticByte`. Earlier incorrect layouts split these across bytes 36/37/38 as three separate fields. Always encode slot 4 as one packed byte and decode with `UnpackSyntacticByte`.
- **[fix]** In `FrameTicker.AppendBracket`, the anchor bracket (`lastIBkt`) must be stored via `cloneBracketShallow(b)`, not as a raw pointer. Storing the raw pointer means subsequent P-frame XOR mutations overwrite the anchor's `Projections` field, silently corrupting drift detection for all future brackets in the same frame.
- **[gotcha]** `packages/KNIRVSERVER/pkg/knirvagent/` is the KNIRVSERVER-side process manager (its own `go.mod`, module `github.com/KNIRV/KNIRV_NETWORK/KNIRVAGENT`). The KNIRVAGENT *binary source* lives at `packages/KNIRVAGENT/` (module `github.com/knirvcorp/knirvagent`). These are two distinct modules — editing one has no effect on the other.
- **[correction]** New library code for the KNIRVAGENT binary must go in `packages/KNIRVAGENT/pkg/<subpackage>/` subdirectories — not at the `cmd/` level and not in `packages/KNIRVSERVER/pkg/knirvagent/`. After changes, rebuild and re-embed: run `go build -o ../KNIRVSERVER/pkg/knirvagent/bin/knirvagent ./cmd/knirvagent/` from inside `packages/KNIRVAGENT/`, then rebuild KNIRVSERVER (which uses `//go:embed bin/knirvagent`).
- **[correction]** All internal inter-service communication uses Unix sockets exclusively; KNIRVGATEWAY is the sole TCP listener the browser reaches — port `8080` by default (`internal/config/config.go`), overridden to `8888` via `GATEWAY_PORT` in `.env.testnet`/`.env.production`. New backend_server (in the sibling `KNIRV_CORP` repo) REST endpoints must be registered under `/api/v1/` (proxied by KNIRVGATEWAY via `backend.sock`); new WebSocket endpoints are registered at the root router (not under `/api/v1/`) and go through the `handleBackendWebSocketProxy` hijacker-based tunnel, not `newSocketProxy`.
- **[context]** `newSocketProxy()` in `packages/KNIRVGATEWAY/internal/server/server.go` uses `httputil.ReverseProxy`, which cannot tunnel WebSocket connections (it strips `Upgrade`/`Connection` headers). This is now handled separately: `handleBackendWebSocketProxy` (registered for `/ws` and `/ws/*`) uses raw `http.Hijacker`-based tunneling instead of `ReverseProxy` for WebSocket traffic. Don't add WS routes via `newSocketProxy`/`ReverseProxy` — use the hijacker-based handler pattern.
- **[fix]** `handleInnerAgentWS` is registered at `/ws/dve/{dveId}/inner/stream/{sessionId}` and `/ws/dve/{dveId}/inner` (fixed 2026-07-29 — previously registered without the `dve` segment, which meant it never matched any real request and was dead code; requests silently fell through to the generic `/ws`/`/ws/*` catch-all and got tunneled to backend_server's `DVEInnerAgentWSHandler` instead). The gateway now terminates inner-agent WS itself by dialing the per-DVE KNIRVAGENT socket (`agent-{dveId}.sock` in `AgentSocketDir`) directly, matching the repo-wide convention that nothing should bypass the gateway. Since these routes are registered before the generic `/ws`/`/ws/*` catch-all, they now correctly intercept inner-agent traffic first; backend_server's `DVEInnerAgentWSHandler` is consequently unreachable for this path (left in place as of this writing, not removed — see the sibling `KNIRV_CORP` repo's `CALIBER_LEARNINGS.md`). Confirmed via repo-wide search that no other client (KNIRV_CORP's CLI, KNIRVCONTROLLER, KNIRVARENA) uses this endpoint — only the KNIRVSERVER frontend does, so this had no other callers to account for.
- **[fix]** When `mcp__plugin_socraticode_socraticode__codebase_search` returns empty `{}` for DVE or KNIRVAGENT queries, the index is likely stale. Fall back immediately to `find <pkg_dir> -type f -name "*.go" | xargs grep -l <term>` to locate relevant files by content.
- **[convention]** KNIRVSERVER REST API routes are versioned under `/api/v1/`. WebSocket routes are registered at the root router outside `/api/v1/` and follow the pattern `/ws/dve/{nodeId}/...`. Do not register WS routes under the versioned prefix.
- **[gotcha]** `dve-verification-iframe.tsx` port-scans `['8081', '8080', '8090']` to discover the gateway. In testnet/production the gateway runs on `:8888`. Set env var `NEXT_PUBLIC_GATEWAY_PORT=8888` (matching the configured gateway port) so the iframe finds the gateway without scanning the wrong ports.
- **[gotcha]** KNIRVHASHER uses TWO distinct Unix sockets: `hasher.sock` (HTTP, headless pipeline run/stop/status) and `hasher-grpc.sock` (gRPC, for data-connector `ExportSecurityData`/`TriggerTraining` calls). Connecting a gRPC client to `hasher.sock` produces the misleading error `http2: failed reading server preface` — it looks like a server crash but is a protocol mismatch. The gRPC socket path is derived as `<hasher_socket_path_without_.sock>-grpc.sock` when `HASHER_GRPC_SOCKET_PATH` is unset.
- **[env]** KNIRVHASHER socket env vars: `HASHER_SOCKET_PATH` → HTTP headless socket; `HASHER_GRPC_SOCKET_PATH` → gRPC socket. The data-connector subprocess only receives `HASHER_GRPC_SOCKET_PATH` if `knirvhasher.ManagerConfig.GRPCSocketPath` is set — it is not passed automatically. Always wire `hasherGRPCSocketPath` into `ManagerConfig.GRPCSocketPath` when constructing the hasher manager in `main.go`. Also: `data-connector`'s `LoadConfig` reads `HASHER_GRPC_SOCKET_PATH` (not `HASHER_SOCKET_PATH`) to dial the server — using the HTTP socket env var here triggers a silent protocol failure.
- **[gotcha]** `HasherExporter` in `internal/services/dve/hasher_export.go` (backend_server source, in the separate sibling `KNIRV_CORP` repo, not under `packages/KNIRVSERVER/` in this repo) defaults to `localhost:50051` when no address is passed — this TCP address is wrong; the backend's gRPC server is on a Unix socket. Any caller must pass `"unix:<hasher-grpc.sock>"` explicitly or the export stream will immediately fail with a connection error.
- **[gotcha]** KNIRVHASHER pipeline stages in `packages/KNIRVHASHER/pipeline/` each have their own `go.mod` with shorthand local module names (`data-connector`, `data-mapper`, `data-encoder`, `data-trainer`; directories are `0_DATA_CONNECTOR`/`1_DATA_MAPPER`/`2_DATA_ENCODER`/`3_DATA_TRAINER`). Each stage must be built and tested from within its own subdirectory — they cannot be imported from or built via the root `packages/KNIRVHASHER/` module.
- **[gotcha]** `packages/KNIRVHASHER/pipeline/2_DATA_ENCODER`'s `AutoDetectInputFile()` searches for its input in `$KNIRV_APP_DATA_DIR/json/` and `~/.local/share/hasher/`, in priority order: `ai_knowledge_base_goat_alpaca.json` → `ai_knowledge_base_alpaca.json` → `ai_knowledge_base.json` → `.arrow` variants. If data-mapper writes output to a different path than expected, the encoder silently falls back to a placeholder that doesn't exist and fails immediately with "input file does not exist".
- **[gotcha]** `packages/KNIRVHASHER/pipeline/0_DATA_CONNECTOR` connects to KNIRVSERVER via TCP gRPC (`grpc.NewClient(config.KNIRVSERVERAddr, grpc.WithTransportCredentials(insecure.NewCredentials()))`). To route through the Unix socket instead, the YAML config `knirvserver_addr` must use the `unix:` scheme (e.g. `unix:/path/to/hasher-grpc.sock`) — the address is passed verbatim to `grpc.NewClient`.
- **[gotcha]** Passing `--goat` to the knirvhasher CLI skips `0_DATA_CONNECTOR` entirely and fetches from HuggingFace (`stallone/goat` dataset) directly. Output filenames change from `ai_knowledge_base.json` to `ai_knowledge_base_goat_alpaca.json` — the encoder's `AutoDetectInputFile()` prefers the goat variant, so the pipeline still flows correctly. Remove `--goat` when you want the data-connector security export path instead.
- **[env]** `KNIRV_APP_DATA_DIR` must be set consistently for all KNIRVHASHER pipeline stages. `data-mapper` writes to `$KNIRV_APP_DATA_DIR/hasher/data/json/`; `data-encoder` reads from `$KNIRV_APP_DATA_DIR/json/`. If the env var differs between stage invocations or is absent in any stage, each falls back to its own directory resolution logic and the stages write/read from different paths, silently breaking the pipeline.
- **[gotcha]** `data-trainer` (CGo binary) links against `libcuda_hash.so` at build time, but the `.so` is NOT automatically included in `internal/cli/embedded/bin/`. At runtime the binary fails immediately with `exit status 127` ("cannot open shared object file"). After `make build-data-trainer`, also ensure `libcuda_hash.so` is present in the embed dir. The Makefile `build-data-trainer` target copies it automatically — older installs or manual builds require: `cp pkg/hashing/methods/cuda/libcuda_hash.so internal/cli/embedded/bin/`.
- **[gotcha]** The `data-trainer` pipeline stage args (`PipelineStage.Args`) must use `-hash-method auto`, not a hardcoded `-hash-method cuda` — hardcoding `cuda` causes `exit status 127` on any machine without a GPU even when `libcuda_hash.so` is present. `auto` falls back gracefully to the software implementation when CUDA is unavailable.
- **[gotcha]** When KNIRVSERVER runs as root (e.g., `sudo ./backend_server`), the `data-mapper`'s embedded C++ Python bridge calls `site.getusersitepackages()` which resolves to `/root/.local/...`, not the invoking user's `~/.local/...`. spaCy models installed for the real user (like `en_core_web_sm`) become invisible and the pipeline fails with `OSError: Can't find model 'en_core_web_sm'`. Fix: `manager.go` now reads `SUDO_USER` and injects the correct `PYTHONPATH`; always start KNIRVSERVER via `sudo -E` or ensure `SUDO_USER` is preserved in the environment.
- **[gotcha]** `data-mapper` has `RUNPATH` baked in at build time pointing to the absolute source-tree path (`packages/KNIRVHASHER/pipeline/1_DATA_MAPPER/spacy/lib`) for `libspacy_wrapper.so`. On deployed machines where the source tree doesn't exist (e.g., `/var/lib/knirvserver/bin/data-mapper`), `ldd` will show `libspacy_wrapper.so => not found` and the NLP bridge silently fails to initialize. Either co-locate `libspacy_wrapper.so` with the binary or set `LD_LIBRARY_PATH` to include the source-tree lib path when running the deployed binary.
- **[gotcha]** `packages/KNIRVSERVER/config/production.yaml` ships with `feature_flags: ebpf: true`, `cognitive_engine: true`, `blockchain_integration: true` — all enabled by default. If a doc or memory claims these are off, it's stale; verify against the YAML directly.
- **[gotcha]** When creating or updating `.socraticodecontextartifacts.json`, verify each artifact path actually exists before adding it. `Write` succeeds even with non-existent paths, and SocratiCode silently skips artifacts that don't resolve — making omissions impossible to diagnose without re-running `codebase_status`. Use `find <path> -maxdepth 1` to confirm paths before inclusion.
- **[gotcha]** The KNIRVARENA arena service creates `arena.sock` only when backend_server successfully **extracts** the embedded `knirvarena.tar.gz` bundle at startup. If `/var/lib/knirvserver/knirvarena/` is empty and `arena.sock` is absent while backend_server is running, the arena `Manager.Start()` failed silently — check logs for "Failed to start KNIRVARENA". The bundle lives at `packages/KNIRVSERVER/pkg/knirvarena/bin/knirvarena.tar.gz` and must be embedded in the built binary before the service is rebuilt and redeployed.
- **[env]** KNIRVGATEWAY reads the env var `ARENA_SOCKET_PATH` (no `KNIRV_` prefix) to configure the `/arena/*` proxy. backend_server propagates it from its own `KNIRV_ARENA_SOCKET_PATH` value to the gateway subprocess. If `ARENA_SOCKET_PATH` is empty in the gateway process, all `/arena/` requests return 502 and the gateway logs "Arena socket path not configured — /arena/* will not be proxied".
- **[gotcha]** KNIRVARENA's `vite.config.ts` must use `base: '/arena/'` and `src/App.tsx` must use `<Router basename="/arena">`. Both must match the gateway's strip-prefix. Changing either without updating the other breaks all asset loading or SPA routing when served behind the gateway.
- **[gotcha]** The arena proxy route chain is: `KNIRVSERVER Gin (/arena/*) → KNIRVGATEWAY (via gateway.sock) → arena.sock`. KNIRVSERVER main.go does NOT proxy `/arena/*` directly to arena.sock — it routes through the gateway, which then proxies to arena.sock. The exact `/arena` path 301-redirects to `/arena/` at the KNIRVSERVER layer before forwarding.
