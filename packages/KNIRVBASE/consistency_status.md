## Critical Issues (Cross-Language Compatibility Breaks)

These issues cause silent failures or data corruption when nodes communicate across language implementations.

---

### CRIT-1 — `ProtocolMessage.Type` field name mismatch (Go vs Rust)

**File:** `go/internal/types/types.go:152`, `rust/src/types.rs:191`

Go serializes the `ProtocolMessage` type field as `"type"` (JSON tag). Rust names the field `msg_type` — with no JSON rename attribute. When a Go node broadcasts a message and a Rust node deserializes it, the `type` field is silently dropped; Rust's `msg_type` stays at its zero value.

```go
// Go
type ProtocolMessage struct {
    Type      MessageType `json:"type"`   // serializes as "type"
    ...
}
```

```rust
// Rust — no #[serde(rename = "type")]
pub struct ProtocolMessage {
    pub msg_type: MessageType,  // deserializes from "msg_type", not "type"
    ...
}
```

**Fix:** Add `#[serde(rename = "type")]` to `msg_type` in `rust/src/types.rs`.

---

### CRIT-2 — JWT tokens are not interoperable (Go vs Rust)

**File:** `go/internal/auth/auth.go`, `rust/src/auth.rs`

Go uses `golang-jwt/jwt/v5` which produces standards-compliant JWTs with **base64url** encoding (RFC 4648 §5, no padding). Rust's custom implementation uses `base64::general_purpose::STANDARD` (standard base64 with `+`, `/`, `=`). A token generated by Go cannot be validated by Rust and vice versa — the signature check will fail on any cross-language auth call.

**Fix:** In `rust/src/auth.rs`, replace `STANDARD as BASE64` with `URL_SAFE_NO_PAD` for both the header/payload encoding and HMAC signature encoding.

---

### CRIT-3 — `MessageType` missing DHT variants (Rust and TS)

**File:** `go/internal/types/types.go:140-149`, `rust/src/types.rs:165-186`, `ts/src/components/types/types.ts:113-120`

Go defines two additional protocol message types for DHT operations that are absent in both Rust and TS:

```go
// Go only
MsgDHTPut MessageType = "dht_put"
MsgDHTGet MessageType = "dht_get"
```

Any Go node sending a DHT message will produce unknown enum values on Rust/TS peers, causing deserialization failures or silent message drops.

**Fix:** Add `DhtPut` / `DhtGet` variants to `rust/src/types.rs` `MessageType` enum and to `ts/src/components/types/types.ts` `MessageType` enum.

---

### CRIT-4 — `MemoryCategory` absent in TS, structurally divergent in Rust

**File:** `go/internal/types/types.go:18-30`, `rust/src/lib.rs:152-193`, `ts/src/components/types/types.ts`

Go defines `MemoryCategory` as a proper string const-type with 9 variants in the shared `types` package (ERROR, CONTEXT, IDEA, SOLUTION, SKILL, GENERIC, EVENT, PREFERENCE, TRAIT). Rust defines an identical-valued but structurally different `MemoryCategory` as a newtype struct in `lib.rs` — not in `types.rs` — so it is not co-located with the rest of the type definitions. TS exports no `MemoryCategory` at all.

Any code routing on `MemoryCategory` from TS will be using raw strings that nothing validates.

**Fix:** Move Rust's `MemoryCategory` into `rust/src/types.rs` as a proper enum. Add `MemoryCategory` enum to `ts/src/components/types/types.ts` and export it from `ts/src/lib/index.ts`.

## High-Severity Issues (Functional Gaps or Data Integrity Risks)

---

### HIGH-1 — PQC crypto is a stub in Rust and TS; only Go uses real Kyber-768

**File:** `go/internal/crypto/pqc/kyber.go`, `rust/src/crypto/pqc.rs`, `ts/src/components/crypto/pqc/keys.ts`

The Go implementation uses the real `cloudflare/circl` library for Kyber-768 KEM + AES-256-GCM hybrid encryption and real Dilithium-3 signatures. The Rust and TS implementations are acknowledged stubs:

- **Rust (`pqc.rs:26`):** `algorithm: "Mock-PQC"`. Keys are 32 random bytes. `verify()` always returns `true`. `sign()` returns random bytes. No actual post-quantum security.
- **TS (`keys.ts:149-151`):** `generateKyberKeyPair()` returns the same random bytes as both public and private key. `kyberEncrypt` is AES-GCM. `dilithiumSign` is HMAC-SHA256.

Keys and ciphertexts from Go are completely incompatible with those from Rust/TS. Any multi-language deployment relying on PQC for security is compromised.

**Fix:** Both Rust and TS need real PQC library bindings (e.g., `pqcrypto` crate in Rust, a WASM-compiled PQC lib in TS) that match the Kyber-768 / Dilithium-3 algorithms used in Go.

---

### HIGH-2 — Security module `encode_key` / `decode_key` use different base64 variants

**File:** `go/internal/security/security.go:95`, `rust/src/security.rs:68`, `ts/src/components/security/security.ts:62`

- Go: `base64.URLEncoding` (URL-safe, with padding)
- Rust: `STANDARD` base64 (standard, with `+`/`/`)
- TS: `Buffer.toString('base64')` (standard base64)

A key encoded by Go cannot be decoded by Rust or TS. This affects any cross-language key transport (e.g., embedding keys in network payloads or config files).

**Fix:** Standardize all three on URL-safe no-padding base64. In Go change to `base64.RawURLEncoding`; in Rust change to `URL_SAFE_NO_PAD`; in TS use `Buffer.toString('base64url')`.

---

### HIGH-3 — Rust `Storage` interface missing KV, JSON, Markdown, and Index APIs

**File:** `go/internal/storage/storage.go:18-46`, `rust/src/storage.rs:10-17`

The Go `Storage` interface defines 14 methods across 5 categories. The Rust trait only implements the 5 collection-level CRUD methods:

| API Category | Go | Rust | TS |
|---|:--:|:----:|:--:|
| Collection CRUD (Insert/Update/Delete/Find/FindAll) | ✅ | ✅ | ✅ |
| KV API (Put/Get/DeleteKey) | ✅ | ❌ | ✅ |
| JSON API (StoreObject/GetObject) | ✅ | ❌ | ✅ |
| Markdown Projection | ✅ | ❌ | ✅ |
| Index Management (CreateIndex/DropIndex/GetIndex/QueryIndex) | ✅ | ❌ | ✅ |

The missing methods in Rust mean `FileStorage` cannot be used for embedding vocabulary persistence, index-accelerated queries, or markdown projection — all of which Go uses in production paths.

**Fix:** Extend `rust/src/storage.rs` `Storage` trait to include the missing API groups, and implement them in `FileStorage`.

---

### HIGH-4 — `TS Claims` missing `session_token` field

**File:** `go/internal/auth/auth.go:22`, `rust/src/auth.rs:41`, `ts/src/components/auth/types.ts:7`

Go and Rust `Claims` both have a `session_token` field supporting hybrid JWT+session tokens. The TS `Claims` interface is missing this field entirely:

```typescript
// TS types.ts — missing session_token
export interface Claims {
  user_id: string;
  wallet_addr: string;
  permissions: Permission[];
  iat?: number; exp?: number; nbf?: number;
  // session_token: string;  <-- absent
}
```

Any TS code parsing a hybrid token (generated by Go or Rust) will silently discard the `session_token`, breaking `ValidateSessionToken` equivalents in TS.

**Fix:** Add `session_token?: string` to the TS `Claims` interface in `ts/src/components/auth/types.ts`.

### HIGH-5 — `ModalityType` semantic mismatch between Go and Rust

**File:** `go/pkg/nrv/spec.go:11-18`, `rust/src/lib.rs:196-214`

These are two completely different enum vocabularies with the same type name:

```go
// Go nrv/spec.go — NRV frame modalities
ModalityVector ModalityType = "vector"
ModalitySeed   ModalityType = "seed"
ModalityThermo ModalityType = "thermo"
ModalityProof  ModalityType = "proof"
```

```rust
// Rust lib.rs — media modalities
ModalityType::Vector / Audio / Video / Image / Text
```

These represent entirely different concepts. The Go variants describe NRV frame data types; the Rust variants describe media content types. Both are exported under the same `ModalityType` name. Any cross-language message containing a `modality_type` field will be misinterpreted.

**Fix:** Rename one of the two. The NRV-specific Go enum should remain as `NRVModalityType`; Rust's media-focused enum should be `MediaModalityType` — or vice versa. Align both with the query parser's usage of `ModalityType` in KNIRVQL.

## Medium-Severity Issues (Correctness and Maintenance Debt)

---

### MED-1 — Rust `save_vocabulary` copy-paste bug in embedding

**File:** `rust/src/embedding/mod.rs:148-159`

```rust
fn save_vocabulary(&self, storage: &Arc<dyn Storage>) -> Result<(), String> {
    let vocab_json = serde_json::to_string(&vectorizer.get_vocabulary())...;
    let idf_json = serde_json::to_string(&vectorizer.get_vocabulary())  // BUG: should be get_idf()
        .map_err(...)?;
    storage.put("embedding:vocabulary", vocab_json.as_bytes())?;
    storage.put("embedding:idf", idf_json.as_bytes())?;
    // MISSING: word_doc_counts and doc_count keys (Go saves 4 keys, Rust saves 2)
}
```

The IDF values are never persisted — `embedding:idf` is overwritten with a second copy of the vocabulary. Additionally, Go persists `embedding:word_doc_counts` and `embedding:doc_count` keys which Rust never saves.

**Fix:** Use `vectorizer.get_idf()` for `idf_json`. Add persistence for `word_doc_counts` and `doc_count`.

---

### MED-2 — Rust `load_vocabulary` does not restore state

**File:** `rust/src/embedding/mod.rs:162-173`

```rust
fn load_vocabulary(&self) -> Result<(), String> {
    let vocab_data = storage.get("embedding:vocabulary")?.ok_or(...)?;
    let _vocab: HashMap<String, usize> = serde_json::from_slice(&vocab_data)...;
    // _vocab is discarded — never written back to self.vectorizer
    Ok(())
}
```

The loaded vocabulary is parsed into a local variable that is immediately dropped. The vectorizer remains empty after a "restore". This means Rust embedding state does not survive restarts despite appearing to succeed.

**Fix:** After deserializing, call `self.vectorizer.write().unwrap().restore_vocabulary(_vocab)` (or equivalent) to actually populate the vectorizer.

---

### MED-3 — Rust has two competing query module files

**File:** `rust/src/query.rs`, `rust/src/query_parser.rs`

`rust/src/lib.rs` imports only `mod query_parser`. The file `rust/src/query.rs` is an orphaned stub (only supports `GET`, no real parsing, returns hardcoded `"default"` collection). It is never compiled into the library and will confuse future contributors.

**Fix:** Delete `rust/src/query.rs`.

---

### MED-4 — Rust `query_parser.rs` execution is incomplete

**File:** `rust/src/query_parser.rs:376-406`

The `execute()` method in Rust handles only `Get`, `Set`, and `Delete`. All other query types (`CreateIndex`, `CreateCollection`, `DropIndex`, `DropCollection`, `GetModality`) return `Err("unsupported query type")`, whereas Go fully implements all of them, including optimizer-assisted index scans.

**Fix:** Implement the missing arms in `Query::execute()`, wiring them to the storage layer's index management methods (which also need to be added per HIGH-3).

---

### MED-5 — TS `query/knirvql.ts` has a duplicated code block

**File:** `ts/src/components/query/knirvql.ts:72-88`

Lines 72–88 and 88–102 are exact duplicates of the `SIMILAR TO` parsing branch within the `WHERE` clause loop. This is a copy-paste artifact that will cause confusion and potential future divergence.

**Fix:** Remove the duplicate block (lines 88–102).

---

### MED-6 — TS missing embedding module entirely

TS has no equivalent of Go's `internal/embedding/` (TF-IDF vectorizer, LSA reducer, `TFIDFEmbedder`). This module underpins semantic similarity search and the `SIMILAR TO` KNIRVQL clause. A TS client cannot perform local embedding or incremental vocabulary updates, degrading to zero-vectors for all similarity queries.

**Fix:** Implement a `ts/src/components/embedding/` module with `TFIDFVectorizer`, `LSAReducer`, and `TFIDFEmbedder` matching Go's interface. Minimum viable: port the TF-IDF transform and normalize-to-target path; the LSA reduction can be a no-op initially.

---

### MED-7 — Rust missing `logging`, `monitoring`, and `tracing` modules

Rust exports none of Go's observability stack:
- **Logging:** Go uses structured Zap logging with `WithBlockID` / `WithUserID` / `WithError` context helpers. Rust has no equivalent structured logger — internal code falls back to `println!` or nothing.
- **Monitoring:** Go exposes 11 Prometheus-backed metrics matching TS's custom metric names. Rust emits no metrics.
- **Tracing:** Go initializes an OpenTelemetry/Jaeger tracer with `StartSpan`. Neither Rust nor TS implements distributed tracing.

**Fix (priority order):**
1. Add a `logging` module to Rust using `tracing` crate that mirrors Go's context fields (`block_id`, `user_id`).
2. Add a `monitoring` module to Rust using `prometheus` crate with the same 11 metric names as Go/TS (`knirvbase_blocks_committed_total`, etc.).
3. Add `tracing` module to both Rust (via `opentelemetry` + `tracing-opentelemetry`) and TS (via `@opentelemetry/sdk-trace-node`).

---

### MED-8 — TS uses `any` where project convention requires `unknown`

**File:** `ts/src/components/types/types.ts:13`, `ts/src/components/types/types.ts:128`

```typescript
payload?: Record<string, any>;      // DistributedDocument — should be unknown
payload: any;                        // ProtocolMessage — should be unknown
```

Project convention (CLAUDE.md): "TypeScript: `unknown` over `any`". These two `any` usages are in the core shared types file and will propagate into all downstream consumers.

**Fix:** Change `Record<string, any>` to `Record<string, unknown>` and `any` to `unknown` in `types.ts`. Update downstream code that casts these as needed.

### LOW-2 — Rust `query.rs` DELETE parser accepts uppercase `ID` but Go accepts lowercase `id`


A DELETE query written for Go (`DELETE WHERE id = x`) will fail on Rust's `query.rs` if case sensitivity differs. This is minor but creates divergent KNIRVQL behavior.
