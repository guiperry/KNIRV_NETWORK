 Root Cause: The CreateDVENode handler held dcs.mu.Lock() for 30-40+ seconds while synchronously performing container provisioning, KNIRVAGENT startup (30s timeout), and chain gRPC calls (10s timeout). This blocked ALL other DVE creation endpoints during that window. The handler eventually panicked when one of these long-running operations failed, producing the ERR_EMPTY_RESPONSE.
    
    Fix: Asynchronous DVE Provisioning
    
    I split DVE creation into two phases:
    
    Phase 1 — Synchronous (fast, <100ms):
    - Validates the request
    - Creates the DVE record with status "pending"
    - Saves to database
    - Returns 201 Created immediately to the frontend
    
    Phase 2 — Asynchronous (background goroutine):
    - Chain registration (best-effort)
    - Container provisioning
    - DVE Manager registration
    - KNIRVAGENT supervisor startup
    - Chain session establishment
    - Creates DVE session
    - Updates status to "active"
    - Saves updated record + session to database
    
    The mutex is only held briefly — during initial record creation (~5μs) and during final status update (~5μs) — instead of for the entire 30-40 second provisioning process.
    
    Files changed:
    1. backend/internal/services/dvecreation/dve_creation_service.go — Refactored CreateDVENode to be async, added provisionDVEInBackground and updateCreationStatus methods
    2. backend/internal/services/dvecreation/dve_creation_service_test.go — Added mutex to MockChainClient for thread safety, updated test expectations for async behavior
