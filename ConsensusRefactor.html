1. Context & Motivation

Problem: KNIRVCHAIN and KNIRVBASE each independently implement P2P consensus with different transport stacks (libp2p vs custom TCP). Neither is optional by default. There is no shared P2P layer, and the gateway's role as a consensus proxy is not formalized for KNIRVBASE.

Goals:

  1. Migrate P2P consensus data sync into KNIRVBASE as the default network layer.
  2. Make both packages P2P-optional with config toggles and CLI fallbacks.
  3. ChainID scopes all KNIRVCHAIN sync; NetworkID scopes all KNIRVBASE sync.
  4. Unified proxy via KNIRVGATEWAY when present; falling back to standalone TCP otherwise.
  5. No cross-package Go imports — three independent implementations following the same pattern.

2.2 Gateway Proxy Flow (Already Working for KNIRVCHAIN)

KNIRVCHAIN → dht/client.go → HTTP POST (Unix socket) → KNIRVGATEWAY
localhost:8080 → libp2p DHT
+ GossipSub → P2P Network

Discovery of gateway: KNIRVCHAIN's GatewayClient (in internal/p2p/gateway_client.go, consolidated from internal/dht/client.go) attempts to connect to the gateway at localhost:8080. If reachable, it registers its Unix socket callback path and delegates all P2P to the gateway. If unreachable, KNIRVCHAIN falls back to direct in-process libp2p via internal/p2p/discovery_manager.go.

4. The Three Consensus Modes

🔷 Mode 1: KNIRVCHAIN Standalone

  • Condition: P2P enabled, gateway unreachable
  • Transport: Direct libp2p TCP
  • Entry: internal/p2p/discovery_manager.go
  • Default: OFF
  • Identity: ChainID
  • Action: Make optional + polish

🟢 Mode 2: KNIRVBASE Standalone

  • Condition: P2P enabled, gateway unreachable
  • Transport: Direct libp2p TCP (not custom TCP)
  • Entry: internal/p2pconsensus/ (NEW)
  • Default: ON
  • Identity: NetworkID
  • Action: Build new

🟣 Mode 3: KNIRVGATEWAY Shared

  • Condition: Gateway running + P2P enabled
  • Transport: Unix socket → gateway libp2p
  • Entry: internal/dht/ + internal/p2pconsensus/gateway_proxy.go
  • Default: ON (when gateway present)
  • Identity: ChainID / NetworkID
  • Action: Extend for KNIRVBASE

5. Shared Gateway Proxy Mode (Default when gateway is present)

5.1 How It Works for KNIRVCHAIN (Already Implemented)

Chain sees gateway on localhost:8080 →
  dht/client.go registers callback socket →
  gateway stores socket path via SetChainCallbackSocket() →
  gateway creates libp2p host + DHT + GossipSub →
    joins {chainID}.blocks and {chainID}.transactions topics →
  chain's P2PConsensusManager can:
    - BroadcastBlock / BroadcastTransaction via POST /p2p/publish-*
    - Receive blocks/txs via gateway → POST /internal/p2p/received-*
    - Request sync via POST /internal/chain/sync
    - Discover peers via /dht/find, /dht/cache-resource

5.2 Extension for KNIRVBASE (New)

The gateway must be extended to support KNIRVBASE as a second proxy client, using NetworkID for topic isolation.

5.2.4 Discovery Logic

In Options / New(): if Options.Consensus.GatewayURL is set and Options.Consensus.Enabled == true, create a GatewayProxy. If the proxy connects successfully, use gateway mode. Otherwise, fall back to standalone mode.

7.3 Standalone Mode Transport

Important: The standalone mode for KNIRVBASE uses libp2p, not the current custom TCP. This is necessary to maintain a consistent transport abstraction between standalone and gateway modes (both use libp2p-style identity, streams, and protocols).

The existing internal/network/ package is deprecated and should be replaced by the new libp2p-based implementation in internal/p2pconsensus/standalone.go.

8. Gateway Presence Discovery

8.1 Algorithm

Both KNIRVCHAIN and KNIRVBASE use the same pattern to determine which transport mode to use:

func detectGateway(gatewayURL string, timeout time.Duration) bool {
    // Attempt GET /p2p/health (or /health) on gatewayURL
    ctx, cancel := context.WithTimeout(context.Background(), timeout)
    defer cancel()
    req, _ := http.NewRequestWithContext(ctx, "GET", gatewayURL+"/p2p/health", nil)
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return false  // gateway not reachable, use standalone
    }
    defer resp.Body.Close()
    return resp.StatusCode == 200
}

Incorporated into Options / Config init:

// KNIRVBASE
cfg := Options.Consensus
if cfg.Enabled {
    if cfg.GatewayURL != "" && detectGateway(cfg.GatewayURL, 2*time.Second) {
        mode = "gateway"
    } else {
        mode = "standalone"
    }
} else {
    mode = "disabled"
}

Gateway unreachable behavior: If the gateway was previously reachable but becomes unreachable, the proxy client should retry with exponential backoff. After n consecutive failures, fall back to standalone mode. When the gateway comes back, switch back to proxy mode.

13. Appendix: Reference Flows

13.1 Gateway Proxy Flow (KNIRVBASE → Gateway → Network)

1. KNIRVBASE starts
2. Options.Consensus.Enabled == true
3. detectGateway("http://localhost:8080", 2s) → true
4. Creates GatewayProxy(gatewayURL, networkID, callbackSocket)
5. GatewayProxy.Register() → POST /knirvbase/register-callback
   { "socket_path": "/tmp/knirvbase.sock", "network_id": "knirvbase-default" }
6. Gateway stores callback socket, creates HTTP client (Unix dialer)
7. Gateway calls SetupCRDTPubSub(networkID) → joins "{networkID}.ops" GossipSub topic
8. KNIRVBASE SocketServer starts listening on /tmp/knirvbase.sock

--- CRDT operation broadcast (KNIRVBASE → Network) ---
9.  distributed_collection.Put(doc)
10. → p2pconsensus.Manager.PublishOperation(op)
11. → GatewayProxy.PublishOperation(ctx, op)
12. → POST /knirvbase/publish-op (JSON body)
13. → Gateway DHTManager.PublishOperation(ctx, op)
14. → publishes to "{networkID}.ops" GossipSub topic
15. → remote peers receive via their gateway subscriptions

--- CRDT operation receive (Network → KNIRVBASE) ---
16. Remote peer publishes to "{networkID}.ops" topic
17. Gateway HandleCRDTOperations() goroutine receives from sub
18. → forwardToBase("/internal/p2p/received-op", opData)
19. → POST /internal/p2p/received-op (via Unix socket HTTP)
20. → KNIRVBASE SocketServer handler
21. → p2pconsensus.Manager.HandleReceivedOperation(op)
22. → distributed_collection.Merge(op)

13.2 Standalone Flow (KNIRVBASE → Direct libp2p → Network)

1. KNIRVBASE starts
2. Options.Consensus.Enabled == true
3. detectGateway("http://localhost:8080", 2s) → false (or Mode == "standalone")
4. Creates StandaloneConsensus(networkID, listenAddr, port, bootstrapPeers)
5. Creates libp2p host + Kademlia DHT + GossipSub
6. Joins "{networkID}.ops" GossipSub topic
7. Connects to bootstrap peers (or waits for mDNS discovery)

--- CRDT operation broadcast ---
8.  distributed_collection.Put(doc)
9.  → p2pconsensus.Manager.PublishOperation(op)
10. → StandaloneConsensus.PublishOperation(ctx, op)
11. → publishes to "{networkID}.ops" GossipSub topic via local libp2p host
12. → remote peers receive directly

--- CRDT operation receive ---
13. Local HandleCRDTOperations() goroutine receives from sub
14. → p2pconsensus.Manager.HandleReceivedOperation(op)
15. → distributed_collection.Merge(op)

13.3 ChainID / NetworkID Isolation

KNIRVCHAIN:
  - DHT protocol prefix:  /KNIRVCHAIN-dht/{ChainID}/{peerID[:8]}
  - GossipSub topics:     {ChainID}.blocks, {ChainID}.transactions
  - Sync request header:  X-Chain-ID: {ChainID}
  - ChromemDB key prefix: {ChainID}:{key}

KNIRVBASE:
  - GossipSub topics:     {NetworkID}.ops
  - Sync request header:  X-Network-ID: {NetworkID}
  - CRDT op envelope:     {NetworkID}:{op_id}

Gateway (when shared):
  - Topics are created per identity string
  - Messages from different identities are isolated at the topic level
  - Callback routing uses identity to determine which socket to forward to

13.4 Key Design Decisions

DD-1: No cross-package Go imports. Three independent implementations share design patterns but are independently maintained.
DD-2: KNIRVCHAIN P2P defaults to OFF. KNIRVBASE P2P defaults to ON. This reflects KNIRVBASE's role as the default network layer.
DD-3: Gateway proxy uses Unix domain socket HTTP, not raw streams. This matches the existing KNIRVCHAIN↔Gateway protocol.
DD-4: KNIRVBASE standalone uses libp2p, not the current custom TCP. This ensures transport consistency between modes and reuses the existing libp2p expertise in the project.
DD-5: CLI flag always overrides config value (defense in depth for P2P disable).
DD-6: Gateway presence discovery is implicit (health check on configured URL). Mode is explicitly configurable as "auto" | "gateway" | "standalone" | "disabled" for operational control.
DD-7: The existing internal/network/ package in KNIRVBASE is deprecated but not removed immediately. Forwarding methods ensure backward compatibility during the transition.

13.5 Gateway GossipSub Topic Naming

// KNIRVCHAIN topics (existing)
{chainID}.blocks
{chainID}.transactions
network_control
graph-announcements

// KNIRVBASE topics (new)
{networkID}.ops           ← CRDT operations
{networkID}.sync          ← sync requests (for pull-based sync)

Topic isolation ensures that KNIRVCHAIN and KNIRVBASE traffic does not interfere, even when both share the same gateway and libp2p host.
