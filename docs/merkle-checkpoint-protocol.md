# Merkle checkpoint and finality protocol

KNIRVCHAIN checkpoints are provisional leaves in KNIRVORACLE's append-only
Merkle Mountain Range (MMR). A checkpoint becomes final only after registered
validation-chain nodes verify its transition proof and submit a two-thirds
quorum of ed25519 attestations. Failure or expiry appends a rejection leaf,
slashes the chain's staking-backed NRN bond, and queues consensus evidence.

## PLONK validity proofs

`knirv.accum-plonk.v1` uses gnark PLONK over BN254. The circuit proves:

- the public pre-accumulator advances to the public checkpoint root;
- every block transaction root is recomputed in-circuit from private,
  domain-separated transaction leaf hashes;
- every active block proposer has a Merkle membership path in the registered
  PoAu-D author set;
- the fixed-capacity private batch is bound to a public SHA-256 batch digest.

Circuit capacity (`max_blocks`, `max_tx_per_block`, and author-tree depth) and
the author-set root are included in the verification-key envelope. Key rotation
is required when those parameters or the author set changes. Production setup
must provide a universal KZG SRS generated by a ceremony. The
`NewUnsafePLONKProver` helper is only for tests and local benchmarks.

The prover runs asynchronously after provisional admission. `hashchain-v0`
remains a degraded fallback and does not halt checkpoint submission; it reveals
the complete batch so validation nodes can recompute each transaction root and
accumulator step before signing.

The default proof window is 256 Oracle blocks (about 21 minutes at the current
five-second target). A cold development KZG setup plus one-block/one-transaction
prove-and-verify cycle measured 174.5 seconds on the implementation host, giving
more than sevenfold headroom. The realistic fixed-capacity generation and
verification benchmarks can be rerun with:

`go test ./internal/checkpoint -run '^$' -bench 'PLONK(Proof|Verify)8Blocks8Tx' -benchtime=1x`

## Endpoints

| Service | Method and path | Purpose |
|---|---|---|
| KNIRVCHAIN | `GET /proof/tx/{hash}?target_height=H` | Transaction → block TxRoot → chain AccumRoot proof |
| Backend internal socket | `POST /internal/verify-checkpoint` | Verify MMR inclusion and PLONK or hashchain fallback proof; sign and submit an attestation |
| Oracle | `POST /oracle/v3/registry/verify-key` | Register a chain's proof-system verification-key envelope |
| Oracle | `GET /oracle/v3/registry/{chain_id}` | Fetch chain authors, bond state, proof system, and verification key |
| Oracle | `POST /oracle/v3/verifiers/register` | Register `{verifier_id, public_key}` for the attestation quorum |
| Oracle | `POST /oracle/v3/finality/attest` | Submit a proof-bound signed verifier attestation |
| Oracle | `POST /oracle/v3/finality` | Submit a complete proof and signed attestation quorum |
| Oracle | `GET /oracle/v3/mmr/root` | Current MMR root and leaf count |
| Oracle | `GET /oracle/v3/mmr/proof/{index}` | Checkpoint/finality/rejection leaf → Oracle MMR root proof |

Byte slices in JSON use standard Go base64 encoding. Hash arrays are 32-element
JSON byte arrays. Verification keys are self-describing JSON envelopes encoded
as a byte slice in the registry request.

## Verifier deployment

Set `KNIRV_VERIFIER_PRIVATE_KEY` to the base64-encoded 32-byte ed25519 seed or
64-byte private key. `KNIRV_VERIFIER_ID` is optional and defaults to the public
key hex. Root deployments use the configured `oracle.sock`; non-root nodes use
`KNIRV_ORACLE_URL`, defaulting to the production or testnet gateway. Public
traffic uses `KNIRV_GATEWAY_TOKEN`.

Register the corresponding 32-byte public key before accepting work. The Oracle
verifies every signature over:

`big_endian(leaf_index) || checkpoint_leaf_hash || approved_byte`

Attestations from unregistered IDs, wrong leaves, duplicate IDs, invalid
signatures, or a different transition proof do not count toward quorum.

## Bonds and slashing

`ChainRegistration.bond` reserves that amount from `bond_owner`'s active NRN
stake. Reserved stake cannot back another chain. The default rejection policy
slashes 10% of the remaining bond (rounded up) for a failed proof or missed
window. The amount is burned with reason `slashing`, reflected in
`bond_remaining`/`bond_slashed`, embedded in the rejection leaf, and queued as
`CheckpointSlashingEvidence` for the next Oracle block.

## Two-hop light-client verification

1. Fetch a final checkpoint record and request the transaction proof with its
   `end_height` as `target_height`.
2. Recompute the canonical transaction leaf and sibling path to `block_tx_root`.
3. Fold the containing block and every subsequent accumulator step. The result
   must equal the checkpoint `root`.
4. Fetch `/oracle/v3/mmr/proof/{mmr_position}` and independently fold the
   checkpoint `leaf_hash` to `/oracle/v3/mmr/root`.

`integration-tests/merkle_two_hop_test.go` is a standalone client implementation
and can run against testnet using the four environment variables documented in
that test.
