Date: 2026-06-02  |  Owner: Platform Engineering

1. Why Keep Both — Division of Responsibility

GraphRAG and KNIRVGRAPH solve different problems. Removing either would lose real capability:

Dimensiongraphrag-rs (Rust, in-process CGo)KNIRVGRAPH (Go, subprocess HTTP)
Primary function RAG engine — text in, knowledge graph + answers out Decentralized graph chain — verifiable DAG of nodes with consensus
Content processing EXISTS — chunking, entity extraction (LLM/GLiNER/regex), relationship extraction MISSING — no text ingestion pipeline
Vector embeddings EXISTS — Candle local, Ollama API, HNSW, Qdrant, LanceDB, Voy MISSING — NRV vectors are 5-dim stubs
Retrieval EXISTS — hybrid, PageRank, LightRAG, HippoRAG, cross-encoder reranking PARTIAL — PageRank, graph traversal exist; no BM25, no ANN index
Answer synthesis EXISTS — LLM answer gen, reasoning traces, critic refinement MISSING — returns structured data only
Graph chain (DAG) MISSING — single in-memory graph instance EXISTS — Merkle DAG, heads, path finding, genesis
Consensus / Economics MISSING EXISTS — Proof-of-Solution, NRN rewards, resolution events
DRQ (Distributed Red Queen) MISSING EXISTS — error clustering, LoRA training, MAP-Elites, agent routing
DVE (Distributed Verification) MISSING EXISTS — sandbox, skill invocation protocol
Persistence Workspace snapshots, Parquet/Arrow, optional BadgerDB, LevelDB, in-memory — production-grade storage
Embedding model EXISTS — multiple providers MISSING

Decision: Keep both. GraphRAG owns content processing → retrieval → synthesis. KNIRVGRAPH owns persistent graph storage → consensus → agent coordination. Wire them so graphrag writes results into KNIRVGRAPH's DAG, and KNIRVGRAPH's DRQ agents can query graphrag for semantic retrieval.

2.2 Two-Way Data Bridge

GraphRAG produces graph data (entities, relationships, chunks) that must flow into KNIRVGRAPH for durable storage and consensus. KNIRVGRAPH's DRQ module needs embedding vectors from graphrag for semantic clustering. This requires a bidirectional bridge:

graphrag_index_document(doc)
  → Rust extracts entities + relationships
  → Result returned to Go (JSON)
  → Go calls KNIRVGRAPH POST /node, POST /edge to persist
  → Go tracks IndexStatus in KNIRVGRAPH metadata store
KNIRVGRAPH DRQ cluster_errors()
  → Sends error descriptions to graphrag for embedding vectors
  → graphrag returns vectors via FFI
  → DRQ performs clustering in Go
  → Results (ErrorCluster, TrainingExample) stored in KNIRVGRAPH DAG

3.2 Root Cause

There are two separate GraphRAG client abstractions that never meet:

  1. pkg/embedded/graphrag/graphrag.go — the real CGo wrapper with working Init(), Shutdown(), HealthCheck(), and correctly typed IndexDocument() / Query() functions that call into Rust.
  2. backend/internal/services/memory/graphrag.go and backend/internal/services/knowledge_base/graphrag_ffi.go — Go-side stub clients that do not call the real CGo wrapper. They manage in-memory Go maps and return placeholder data.

The services (UnifiedMemorySystem, KnowledgeBaseService) talk to #2. The embedded manager talks to #1. They never exchange a byte.

5.2 Phase 2 — Unified GraphRAG Client (Week 2)

Goal: The new graphrag.Client is fully wired, all stubs replaced, auto-sync works end-to-end.

5.2.1 Implement pkg/embedded/graphrag/client.go

package graphrag

import (
    "context"
    "encoding/json"
    "fmt"
    "sync"
    "time"
)

type Client struct {
    mu      sync.RWMutex
    indexes map[string]*Index
}

type Index struct {
    KBID        string
    Status      string  // "not_built", "building", "ready", "error"
    NodesCount  int
    EdgesCount  int
    ChunksCount int
    LastUpdated time.Time
    Err         error
}

func NewClient() *Client {
    return &Client{indexes: make(map[string]*Index)}
}

func (c *Client) Query(ctx context.Context, kbID string, q *Query) (*Result, error) {
    // 1. Verify index exists and is ready
    // 2. Build FFI query JSON: {"query": q.Query, "mode": q.Mode, "limit": q.Limit}
    queryJSON, _ := json.Marshal(map[string]interface{}{
        "query": q.Query,
        "mode":  q.Mode,
        "limit": q.Limit,
        "kb_id": kbID,
    })
    // 3. Call C FFI
    raw, err := graphrag.Query(string(queryJSON), q.Limit)
    if err != nil {
        return nil, fmt.Errorf("graphrag query failed: %w", err)
    }
    // 4. Parse result
    var result Result
    if err := json.Unmarshal(raw, &result); err != nil {
        return nil, fmt.Errorf("graphrag result parse failed: %w", err)
    }
    return &result, nil
}

func (c *Client) BuildIndex(ctx context.Context, kbID string, strategy string) (*IndexStatus, error) {
    c.mu.Lock()
    c.indexes[kbID] = &Index{KBID: kbID, Status: "building"}
    c.mu.Unlock()

    go func() {
        // Load documents from KB (via callback or storage)
        // For each doc: graphrag.IndexDocument(id, content)
        // On completion: update status to "ready" with counts
    }()

    return &IndexStatus{KBId: kbID, Status: "building"}, nil
}

func (c *Client) GetIndexStatus(ctx context.Context, kbID string) (*IndexStatus, error) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    idx, ok := c.indexes[kbID]
    if !ok {
        return &IndexStatus{KBId: kbID, Status: "not_built"}, nil
    }
    return &IndexStatus{
        KBId:        idx.KBID,
        Status:      idx.Status,
        NodesCount:  idx.NodesCount,
        EdgesCount:  idx.EdgesCount,
        ChunksCount: idx.ChunksCount,
        LastUpdated: idx.LastUpdated,
    }, nil
}

func (c *Client) Close() error {
    return graphrag.Shutdown()
}

5.3 Phase 3 — KNIRVGRAPH Persistence Backend (Weeks 3-4)

Goal: Every entity and relationship that graphrag extracts is persisted in KNIRVGRAPH's DAG. KNIRVGRAPH stores index metadata and can serve graph traversal queries against the same data.

5.3.1 Add FFI Result → KNIRVGRAPH Commit Pipeline

In pkg/embedded/graphrag/client.go, after graphrag.IndexDocument() succeeds, extract the entities and relationships from graphrag's internal state and commit them to KNIRVGRAPH:

// After graphrag.IndexDocument:
// graphrag returns JSON with extracted entities and relationships
// We need to add an FFI function to retrieve them:
//   graphrag_get_extracted(doc_id) -> JSON {entities: [...], relationships: [...]}

// Or modify IndexDocument to return extracted data synchronously:
func (c *Client) IndexDocument(ctx context.Context, docID string, content []byte) (*ExtractionResult, error) {
    raw, err := graphrag.IndexDocumentWithResult(docID, content) // new FFI: returns JSON
    if err != nil {
        return nil, err
    }
    var result ExtractionResult
    json.Unmarshal(raw, &result)

    // Commit entities to KNIRVGRAPH
    for _, entity := range result.Entities {
        node := knirvclient.GraphNode{
            NodeID: entity.ID,
            Type:   entity.Type,
            Data:   entity.Properties,
        }
        c.knirvgraph.CommitNode(ctx, node, "extracted by graphrag", "graphrag-bridge")
    }
    // Commit relationships as edges
    for _, rel := range result.Relationships {
        edge := knirvclient.Edge{
            EdgeID:   rel.ID,
            SourceID: rel.SourceID,
            TargetID: rel.TargetID,
            Type:     rel.Type,
            Weight:   rel.Weight,
        }
        c.knirvgraph.CreateEdge(ctx, edge)
    }
    return &result, nil
}

5.3.2 Add New FFI Function to graphrag-rs

In graphrag-core/src/ffi.rs, add a new export that returns extracted entities:

#[no_mangle]
pub extern "C" fn graphrag_get_last_extraction(
    result_len: *mut usize,
) -> *mut c_char {
    // Returns JSON of the most recently indexed document's extractions
    let extraction = match lock_instance(|g| g.last_extraction_json()) {
        Some(json) => json,
        None => return std::ptr::null_mut(),
    };
    if !result_len.is_null() {
        unsafe { *result_len = extraction.len() };
    }
    to_raw_cstring(extraction)
}

On the Rust GraphRAG struct, add a field to cache the last extraction result, populated during add_document_from_text() → build_graph().

func EmbedTexts(texts []string) ([][]float32, error) {
    input, _ := json.Marshal(texts)
    cInput := C.CString(string(input))
    defer C.free(unsafe.Pointer(cInput))

    var bufLen C.size_t
    resultPtr := C.graphrag_embed_texts(cInput, C.size_t(len(input)), &bufLen)
    if resultPtr == nil {
        return nil, fmt.Errorf("embed texts returned null")
    }
    defer C.graphrag_free_string(resultPtr)

    raw := C.GoBytes(unsafe.Pointer(resultPtr), C.int(bufLen))
    var embeddings [][]float32
    json.Unmarshal(raw, &embeddings)
    return embeddings, nil
}

8. Risk Register

RiskLikelihoodImpactMitigation
Rust FFI panics crash the Go process Medium High Wrap every FFI call in recover-safe CGo guard. Add panic hook in Rust that catches and returns error codes instead of unwinding.
CGo cross-compilation breaks for target platform Medium High Document required Rust target toolchains in CI. Test on linux/amd64 first; defer other targets.
GraphRAG static lib size inflates KNIRVSERVER binary Low Medium Already linked; ~15 MB overhead. OK for production. Strip debug symbols.
graphrag_query() is sync — blocks Go goroutine High Medium Wrap in go goroutine with context timeout. GraphRAG's Rust uses tokio::runtime::Runtime::new() inside the FFI call already — it has its own async. Acceptable for now. Long-term: add graphrag_query_async with callback.
DRQ ↔ GraphRAG embedder coupling creates circular dependency Low Medium KNIRVGRAPH only calls embedding_model.Provider interface — no direct graphrag import. The Provider implementation lives in KNIRVSERVER and is injected at startup.
text-embedder conflicts with graphrag's internal embeddings Low Low They are independent providers selected by config. No shared state.
Two FFI init paths collide (manager.go vs client.go) Medium Medium graphrag.Init() is idempotent via INSTANCE: Mutex> — calling it twice replaces the instance. Ensure manager.go inits first, client.go reuses. Or make client.go check HealthCheck() before calling init.
